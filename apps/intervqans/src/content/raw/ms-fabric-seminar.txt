=====

Microsoft introduced Fabric publicly at Microsoft Build on May 23, 2023, initially in preview, and it became generally available in November 2023. The core idea was to bring Microsoft's previously separate analytics technologies—Power BI, Data Factory, Synapse-style engineering/warehousing, real-time analytics, and data science—into one SaaS analytics platform centered around OneLake.


Microsoft Fabric — 1-Hour Conceptual & Technical Seminar
Page 1 — First: What exactly is Microsoft Fabric?
The simplest definition:
Microsoft Fabric is Microsoft's unified, end-to-end data and analytics platform.
It allows an organization to:
collect → store → clean → transform → analyze → model → visualize → monitor → act on data
without stitching together many separate platforms.
Microsoft currently describes Fabric as a SaaS analytics platform supporting ingestion, transformation, real-time processing, analytics and reporting, with experiences including Data Factory, Data Engineering, Data Science, Data Warehouse, Real-Time Intelligence, Databases and Power BI.
Before Fabric
Imagine a company had:

```
SQL Server
   ↓
Azure Data Factory
   ↓
Azure Data Lake
   ↓
Databricks / Synapse Spark
   ↓
Synapse Warehouse
   ↓
Power BI Dataset
   ↓
Power BI Report
```

Technically, this works.
But now you have:

*  different services
*  different security models
*  different billing
*  different administration
*  different storage locations
*  data copies
*  separate monitoring
*  separate development experiences

Fabric's idea is:

```
             MICROSOFT FABRIC

 Data Factory
      ↓
 Data Engineering
      ↓
    OneLake
      ↓
 Lakehouse / Warehouse
      ↓
 Semantic Model
      ↓
   Power BI
```

All under one platform.
Simple analogy
Think about smartphones before the iPhone.
You might have had:
camera + GPS + MP3 player + phone + calculator + browser
as separate devices.
The smartphone didn't invent all those capabilities.
It unified them into one platform.
Fabric is trying to do something similar for enterprise analytics.

This is probably the most important conceptual question.
The problem wasn't:
"Companies don't have enough data tools."
It was almost the opposite.
Companies had too many disconnected data tools.
Microsoft itself described the analytics landscape at Fabric's introduction as fragmented, with specialized services that organizations had to integrate themselves.

It has:


Page 3 — OneLake: the heart of Fabric

If you remember only one Fabric concept after the seminar:

OneLake

Microsoft's own analogy is essentially:

OneLake is to enterprise data what OneDrive is to files.

OneLake is the unified logical data lake for a Fabric organization and is built on Azure Data Lake Storage technology. It is provisioned as part of Fabric rather than requiring every team to build its own separate lake infrastructure.

Conceptually:

```
                    COMPANY

                     OneLake
                        │
        ┌───────────────┼────────────────┐
        │               │                │
      Sales          Finance             HR
        │               │                │
   Lakehouse         Warehouse       Lakehouse
```

Instead of:

```
Sales Lake
Finance Lake
Marketing Lake
HR Lake
Analytics Lake
AI Lake
```

you get a common logical storage foundation.
Why is that important?
Because traditionally:

```
Original Data
     ↓
Copy for Data Lake
     ↓
Copy for Warehouse
     ↓
Copy for Analytics
     ↓
Copy for Power BI
```

creates:
data duplication + storage cost + synchronization problems + governance problems.
Fabric's architecture is designed so multiple workloads can operate over OneLake instead. Microsoft states that Fabric workloads can read and write the same underlying OneLake data without repeatedly moving it between engines.

Page 5 — Lakehouse vs Warehouse
This is one of the biggest Fabric concepts.
Traditional Data Lake
Very flexible:

```
CSV
JSON
Images
Logs
Parquet
Documents
```

But historically less convenient for classic BI.
Traditional Data Warehouse
Very structured:

```
Customers
Products
Sales
Orders
Dates
```

Excellent for SQL and BI.
But less flexible for raw/semi-structured data and data-science workflows.
Lakehouse
The idea is:
Data Lake flexibility + Data Warehouse structure
You can have:

```
Lakehouse
│
├── Files
│   ├── CSV
│   ├── JSON
│   └── Parquet
│
└── Tables
    ├── Customers
    ├── Products
    └── Sales
```

Fabric commonly stores analytical tables using:
Delta + Parquet
Parquet provides efficient columnar storage.
Delta adds capabilities around transactional table management.
When would I choose what?
Think:
Lakehouse
"My engineers use Spark/Python and we're working with raw + structured data."
Warehouse
"My team primarily thinks in relational tables, T-SQL, dimensional models and BI."
In real enterprise architectures, you may use both.

Page 6 — Medallion Architecture
Now we move into real data-engineering architecture.
Microsoft recommends the Medallion architecture as a design approach for Fabric lakehouses.

It has three stages:
           RAW DATA
              ↓
        🥉 BRONZE
          Raw data
              ↓
        🥈 SILVER
       Cleaned data
              ↓
         🥇 GOLD
      Business-ready
              ↓
          Power BI
Bronze
Store data basically as received.
Customer_ID = "001"
Country = "usa"
Date = "8/12/26"
Don't aggressively modify it.
Why?
Because Bronze is your historical/raw reference.
Silver
Clean and standardize.
Customer_ID = 1
Country = "United States"
Date = 2026-08-12
Operations may include:
remove duplicates
handle nulls
standardize dates
validate records
join reference data
correct data types
Gold
Business-ready data.
For example:
FactSales
DimCustomer
DimProduct
DimDate
DimStore
Now Power BI can consume this efficiently.
Simple analogy
Think about cooking vegetables.
Bronze: vegetables straight from the grocery bag.
Silver: washed, peeled and chopped.
Gold: cooked, seasoned and plated.
Power BI shouldn't ideally be spending its time washing vegetables.
It should receive the finished plate.

Page 7 — Direct Lake: one of Fabric's most important innovations
Power BI traditionally gives you two famous choices.
Import
Database
   ↓
COPY DATA
   ↓
Power BI Memory
Advantages:
Very fast
Problem:
You have another copy and need refreshes.
DirectQuery
Power BI
   ↓
SQL query
   ↓
Database
Advantages:
Fresh data.
Problem:
Performance depends heavily on the underlying source/query path.
Direct Lake
Fabric introduces another important storage mode:
               Power BI
                   ↓
            Semantic Model
                   ↓
              Direct Lake
                   ↓
               OneLake
                   ↓
           Delta / Parquet
Direct Lake is designed for Power BI semantic models over Delta tables in OneLake. Queries use the VertiPaq engine, while required columns can be loaded from OneLake on demand. Unlike Import, it doesn't require copying the entire model into an imported dataset during each refresh.
A simplified comparison:
	Import	DirectQuery	Direct Lake
Copies entire data	Yes	No	No traditional full import
VertiPaq	Yes	No	Yes
Large data	Limited by model/capacity	Good	Designed for it
Refresh dependency	Yes	Less	Metadata/framing model
Typical interactive performance	Excellent	Source-dependent	Often close to Import
Important technical nuance: Direct Lake isn't magic. Performance still depends on good Delta-table design, file organization, row groups, semantic-model design and capacity sizing.

Think of a Windows shortcut.

The shortcut doesn't duplicate your 20 GB movie.

It points to where the movie exists.

Security and governance

Enterprise analytics isn't just:

"Can we make a dashboard?"

It's also:

"Should Raja be allowed to see Finance payroll?"

Fabric has platform-level governance and security capabilities, including integration with Microsoft Entra identity and Microsoft Purview-backed governance. The OneLake Catalog provides centralized discovery and governance of Fabric data and analytics artifacts.

Fabric Capacity — how compute fits in
One thing beginners often misunderstand:
OneLake is storage.
Fabric Capacity provides compute resources.
Think:
OneLake = warehouse where your goods are stored.
Fabric Capacity = workers and machines processing those goods.
Fabric capacities use Capacity Units (CUs), with Fabric capacity SKUs such as:
F2
F4
F8
F16
F32
F64
...
Different workloads—Power BI queries, Spark jobs, pipelines, warehouse queries, etc.—consume capacity resources.
This is why enterprise Fabric architecture also involves:
performance engineering + workload management + capacity planning + cost governance.

The 30-second explanation you should eventually be able to give
If someone asks:
"What is Microsoft Fabric?"
A strong answer is:
Microsoft Fabric is Microsoft's unified SaaS platform for end-to-end data and analytics. It brings capabilities such as Data Factory, Data Engineering, Lakehouse, Data Warehouse, Data Science, Real-Time Intelligence and Power BI into a common environment built around OneLake. The major architectural benefit is that different analytics workloads can work against a shared data foundation instead of organizations constantly copying data and integrating separate services. Fabric can take data from ingestion through transformation, modeling and ultimately Power BI reporting or real-time analytics.
That sounds much stronger than:
"Fabric is a new Microsoft BI tool."
Because Fabric is much bigger than Power BI.
The 10 concepts I would make sure everyone leaves knowing

1. Fabric = unified analytics SaaS platform.
2. OneLake = common organizational data lake.
3. Data Factory = ingestion/orchestration.
4. Lakehouse = lake flexibility + structured analytics.
5. Warehouse = SQL-centric enterprise analytics.
6. Spark/Notebooks = engineering and transformation.
7. Bronze → Silver → Gold = progressive data refinement.
8. Semantic Model = business meaning and analytics layer.
9. Direct Lake = Power BI accessing OneLake-backed Delta data without traditional full Import copying.
10. Power BI = consumption/analytics layer inside the broader Fabric ecosystem.

If those ten ideas are clear, the rest of Fabric starts fitting naturally into place.
